\chapter{СИСТЕМИЙН ХЭРЭГЖҮҮЛЭЛТ}

Энэ бүлэгт өмнөх бүлгүүдэд тодорхойлсон шаардлага, архитектур, өгөгдлийн загварт тулгуурлан боловсруулсан дадал төлөвшүүлэх системийн хэрэгжүүлэлтийг тайлбарлана. Үүнд ашигласан технологийн багц, кодын сангийн бүтэц, өгөгдлийн сан, зан үйлийн дүрмүүд, сервер болон хэрэглэгчийн талын үндсэн хэсгүүд, API-ийн зохион байгуулалт, интерфэйсийн шийдлүүдийг авч үзнэ.

Эцсийн хувилбарт хэрэглэгч бүртгүүлэх, нэвтрэх, дадал үүсгэх, хуваарь болон өдөөгч нөхцөл тохируулах, төхөөрөмжийн мэдэгдэл авах, гүйцэтгэл бүртгэх, ахицын статистик харах, дадлын хүчний оноо болон зөвлөмж авах, амжилт болон XP цуглуулах, санал хүсэлт илгээх зэрэг үндсэн урсгалууд хэрэгжсэн.

\section{Технологийн багц}

Эцсийн системийн хэрэгжүүлэлтэд ашигласан үндсэн технологиуд:

\begin{itemize}
  \item \textbf{Сервер талын хүрээ:} NestJS v11 --- модульчилсан зохион байгуулалттай, REST API хөгжүүлэхэд тохиромжтой.
  \item \textbf{Хөгжүүлэлтийн хэл:} TypeScript --- статик төрлийн шалгалтаар кодын найдвартай байдлыг нэмэгдүүлсэн.
  \item \textbf{ORM ба миграц:} Prisma v7 --- схемд суурилсан өгөгдлийн загварчлал, миграцийн удирдлагыг хялбаршуулсан.
  \item \textbf{Өгөгдлийн сан:} PostgreSQL --- харилцаат өгөгдлийн бүтэцтэй системд найдвартай, өргөтгөх боломжтой.
  \item \textbf{Хэрэглэгчийн талын хүрээ:} React 19 + Vite 8 --- бүрэлдэхүүнд суурилсан интерфэйсийн хөгжүүлэлт болон хурдан бүтээлт.
  \item \textbf{Чиглүүлэлт ба өгөгдлийн төлөв:} React Router, React Query --- нэг хуудсын програмын чиглүүлэлт, серверийн өгөгдлийн кэш.
  \item \textbf{Интерфэйс:} Tailwind CSS 4, Radix UI, өөрийн дизайны бүрэлдэхүүнүүд --- тогтвортой, дахин ашиглагдах интерфэйсийн хэв маяг.
  \item \textbf{Анимаци ба газрын зураг:} Motion --- төлөвийн өөрчлөлтийг харуулах; Leaflet --- сануулгын байршлыг газрын зураг дээр сонгох.
  \item \textbf{Баталгаажуулалт:} JWT --- сервер талд хэрэглэгчийн төлөв хадгалахгүй хандалтын хяналт; нэвтрэх үйлдэлд хүсэлтийн тооны хязгаар.
  \item \textbf{Мэдэгдэл ба хуваарьт ажил:} Web Push (VAPID), \texttt{@nestjs/schedule} --- сануулгыг минут тутам шалгаж хүргэх.
  \item \textbf{Баримтжуулалт ба тест:} Swagger (OpenAPI), Jest --- API-ийн тайлбар болон дүрмүүдийн нэгжийн тест.
\end{itemize}

Сервер болон хэрэглэгчийн тал TypeScript хэл дээр хэрэгжсэн тул өгөгдлийн бүтэц, сонголтын төрөл, интерфэйсийн тодорхойлолтыг хоёр талд нийцтэй байлгах боломж бүрдсэн. Ингэснээр API-ийн гэрээний зөрчил, төрлийн алдааг хөгжүүлэлтийн шатанд илрүүлэхэд дөхөм болсон.

\section{Кодын сангийн бүтэц}

Системийг хэрэглэгчийн тал болон сервер тал гэсэн хоёр үндсэн хэсэгт хуваан хэрэгжүүлсэн. Сервер талд зан үйлийн дүрэм, хэрэглээний үйлчилгээ, өгөгдөл хадгалах дэд бүтцийг ялгасан бол хэрэглэгчийн талд дэлгэц, дахин ашиглах бүрэлдэхүүн, сервертэй холбогч, хэрэглэгчийн төлөвийг тусгаарласан.

\subsection{Сервер талын бүтэц}

Сервер тал нь NestJS-ийн модульчилсан бүтэцтэй бөгөөд бизнесийн дүрэм, хэрэглээний урсгал, өгөгдлийн түвшнийг ялгах зарчмыг баримталсан.

\begin{lstlisting}[language=bash, caption={Сервер талын директорийн бүтэц}]
backend/src/
  auth/           -- бүртгэл, нэвтрэлт, JWT баталгаажуулалт
  habits/         -- дадал, хуваарь, SRBAI, дадлын хүч
  progress/       -- гүйцэтгэл, ахиц, санал сэтгэгдэл, зөвлөмж үүсгэх
  reminders/      -- сануулгын шийдвэр, хуваарьт ажил, үйлдэл
  push/           -- вэб мэдэгдлийн бүртгэл ба хүргэлт
  engagement/     -- XP ба амжилтын тэмдэг
  learning/       -- зөвлөмж ба суралцах агуулгын харилцан үйлчлэл
  feedback/       -- аппын санал хүсэлт
  analytics/      -- хэрэглээний идэвхийн бүртгэл

\end{lstlisting}

\subsection{Хэрэглэгчийн талын бүтэц}

Хэрэглэгчийн тал нь дэлгэц, интерфэйсийн бүрэлдэхүүн, сервертэй холбогч, нэвтрэлтийн төлөв, туслах сангууд гэсэн бүтэцтэйгээр зохион байгуулагдсан.

\begin{lstlisting}[language=bash, caption={Хэрэглэгчийн талын директорийн бүтэц}]
frontend/src/
  pages/          -- үндсэн дэлгэцүүд
  components/     -- дахин ашиглагдах интерфэйсийн бүрэлдэхүүнүүд
  features/       -- суралцах хэсэг, баяр хүргэлт, заавар, дадлын маягт
  api/            -- HTTP холбогч ба үйлчилгээний хаягууд
  lib/            -- огноо, төлөв, мэдэгдэл зэрэг туслах функцууд
  context/        -- нэвтрэлт болон ерөнхий төлвийн орчин
  shared/design/  -- өнгө, бичвэр, товчлуурын дизайны тодорхойлолт
\end{lstlisting}

Ийм бүтэц нь хөгжүүлэлтийн явцад хэсгүүдийн хариуцлагыг тодорхой байлгах, цаашид өргөтгөх болон засварлах ажлыг хөнгөвчлөхөд чиглэсэн.

\section{Өгөгдлийн сангийн хэрэгжүүлэлт}

Өгөгдлийн сангийн бүтцийг Prisma ORM-ийн \texttt{schema.prisma} файлд тодорхойлж, PostgreSQL дээр миграцийн аргаар хэрэгжүүлсэн. Системийн төв өгөгдлийн нэгж нь \texttt{Habit} хүснэгт бөгөөд дадлын нэр, хэмжилтийн тохиргоо, эхлэх хугацаа, төлөв, сануулгын идэвхтэй эсэх зэрэг гол шинжүүдийг хадгална.

\begin{lstlisting}[language=SQL, caption={Дадлын үндсэн загвар}]
model Habit {
  id              String               @id @default(uuid())
  userId          String               @map("user_id")
  title           String
  measurementUnit String               @map("measurement_unit")
  targetValue     Float                @map("target_value")
  minimumTarget   Float                @map("minimum_target")
  startDate       DateTime             @map("start_date") @db.Date
  status          HabitLifecycleStatus @default(ACTIVE)
  reminderEnabled Boolean              @default(false)

  scheduleDays      HabitScheduleDay[]
  cues              HabitCue[]
  motivationProfile HabitMotivationProfile?
  logs              HabitLog[]
  reminders         Reminder[]
  srbaiAssessments  SrbaiAssessment[]
  reminderPolicy    ReminderPolicy?
}
\end{lstlisting}

Дадлын гүйцэтгэлийн бүртгэлийг хадгалах \texttt{HabitLog} загварт зөвхөн ``хийсэн'' эсэх төдийгүй тухайн үйлдэл ямар нөхцөлд хийгдсэнийг илэрхийлэх \texttt{completionHour} (Улаанбаатарын цагаар гүйцэтгэсэн цаг), \texttt{coarseLocation} (тухайн үед байсан хадгалсан газар) талбаруудыг тодорхойлсон. Мөн гүйцэтгэлийн эх үүсвэрийг \texttt{CompletionTriggerSource} сонголтын төрлөөр ангилан хадгалдаг. \texttt{logDate} нь гүйцэтгэлийн Улаанбаатарын цагийн бүсийн огноо бөгөөд \texttt{(habitId, logDate)} давтагдашгүй түлхүүрээр нэг дадалд өдөрт нэгээс илүү бүртгэл үүсэхээс өгөгдлийн сангийн түвшинд сэргийлдэг.

\begin{lstlisting}[language=SQL, caption={Гүйцэтгэлийн бүртгэлийн загвар}]
model HabitLog {
  status           HabitLogStatus      // DONE: доод зорилтод хүрсэн
  actualValue      Float?
  completedAt      DateTime
  logDate          DateTime @db.Date   // Улаанбаатарын өдөр
  triggerSource    CompletionTriggerSource @default(UNKNOWN)
  linkedReminderId String?
  completionHour   Int?
  coarseLocation   String?

  @@unique([habitId, logDate])
}
\end{lstlisting}

\section{Зан үйлийн дүрмийн хэрэгжүүлэлт}

Энэхүү системийн онцлог нь зан үйлийн дэмжлэгийн логикийг энгийн үүсгэх, унших, засах, устгах үйлдлээс ялган тусдаа дүрмийн түвшинд (\texttt{src/domain/rules}) хэрэгжүүлсэнд оршино. Сануулга өгөх эсэхийг шийдэх, гүйцэтгэлийн эх үүсвэрийг ангилах, дадлын хүчийг тооцоолох, дасан зохицох зөвлөмж гаргах зэрэг нь өгөгдлийн сантай шууд харьцахгүй, төлөв хадгалахгүй дүрмийн хэлбэрээр боловсруулагдсан бөгөөд дүрэм бүр нэгжийн тесттэй. Өдрийн хил, гарагийг серверийн байршлаас үл хамааран Улаанбаатарын цагийн бүсээр тооцдог.

\subsection{Сануулгын шийдвэрийн дүрэм}

\texttt{ReminderDecisionRules} нь тухайн мөчид сануулга үүсгэх эсэхийг шийдвэрлэнэ. Энэхүү дүрэм нь дараах үндсэн шалгууруудыг авч үздэг.

\begin{itemize}
    \item тухайн дадалд сануулга идэвхтэй эсэх;
    \item өнөөдөр хуваарьт өдөр мөн эсэх;
    \item идэвхтэй өдөөгч нөхцөл байгаа эсэх.
\end{itemize}

Дээрх нөхцөлийг шалгасны үндсэн дээр \texttt{SHOULD\_REMIND}, \texttt{REMINDER\_DISABLED}, \texttt{NOT\_SCHEDULED\_TODAY}, \texttt{NO\_ACTIVE\_CUES} зэрэг шалтгаануудын аль нэгээр шийдвэр гаргана.

\begin{lstlisting}[language=JavaScript, caption={Сануулгын шийдвэрийн дүрэм}]
export class ReminderDecisionRules {
  static decide(
    input: ReminderDecisionInput,
    now: Date = new Date(),
  ): ReminderDecisionResult {
    const isScheduledToday =
      CueScheduleRules.isScheduledToday(input.scheduleDays, now);
    const activeCues = CueScheduleRules.getActiveCues(input.cues);
    const activeCueCount = activeCues.length;

    let reason: ReminderDecisionReason;

    if (!input.reminderEnabled) {
      reason = ReminderDecisionReason.REMINDER_DISABLED;
    } else if (!isScheduledToday) {
      reason = ReminderDecisionReason.NOT_SCHEDULED_TODAY;
    } else if (activeCueCount === 0) {
      reason = ReminderDecisionReason.NO_ACTIVE_CUES;
    } else {
      reason = ReminderDecisionReason.SHOULD_REMIND;
    }

    return {
      shouldRemind: reason === ReminderDecisionReason.SHOULD_REMIND,
      reason,
      isScheduledToday,
      activeCueCount,
      evaluatedAt: now.toISOString(),
    };
  }
}
\end{lstlisting}

Хуваарьт ажил минут бүр идэвхтэй дадлуудыг шалгахдаа эхлээд \texttt{CueWindowRules} дүрмээр ``цаг ба газар'' нөхцөлийг шалгана. Одоогийн Улаанбаатарын цаг дадлын идэвхтэй цагийн хүрээнүүдийн аль нэгэнд багтах ёстой (шөнө дундыг дамнасан хүрээг дэмжинэ); цагийн хүрээгүй дадалд хуваарьт сануулга илгээхгүй. Дадалд байршлын нөхцөл тохируулсан бол хэрэглэгчийн хамгийн сүүлийн байршил 30 минутаас хуучираагүй, тухайн газраас 100 метрийн дотор байх ёстой. Байршлыг хэрэглэгч зөвшөөрсөн үед л апп мэдээлдэг.

Нөхцөл бүрдсэн үед \texttt{ReminderExecutionService} дараах шалгалтуудыг хийнэ: тухайн өдөр дадал аль хэдийн хийгдсэн эсэх, сануулгын бодлогын өдрийн дээд тоонд хүрсэн эсэх (зөвхөн төхөөрөмжид хүргэгдсэн сануулгыг тоолно), өмнөх сануулгын хүлээлгийн хугацаа (\texttt{cooldownMinutes}) дуусаагүй эсэх. Сануулгыг хадгалж, вэб мэдэгдлээр илгээсний дараа хүргэгдсэн эсэхийг тусад нь бүртгэнэ. Өмнөх өдрүүдийн хариулаагүй сануулгыг хугацаа дууссан (\texttt{EXPIRED}) төлөвт шилжүүлдэг.

\subsection{Дадлын хүчний тооцоолол}

\texttt{HabitStrengthRules} нь дадлын хүчийг илэрхийлэх хэд хэдэн зан үйлийн үзүүлэлтийг тооцоолдог. Үүнд:

\begin{itemize}
    \item SRBAI-ийн нормчлогдсон оноо;
    \item хуваарийн биелэлт буюу сүүлийн 28 хоногийн төлөвлөсөн өдрүүдээс хийсэн хувь;
    \item нөхцөл байдлын тогтвортой байдал;
    \item өөрийн санаачилгатай гүйцэтгэлийн хувь (сануулгын бодлогыг тодорхойлоход ашиглана).
\end{itemize}

Үндсэн дэлгэц болон ахицын шинжилгээ хоёулаа ижил \texttt{evaluateComposite} функцээр тооцдог тул нэг дадалд хоёр өөр оноо гарахгүй.

\subsubsection*{SRBAI-ийн оноо}

SRBAI-ийн 4 асуултын хариултаас дундаж түүхий оноог гаргаж, үүнийг 0--100 хооронд нормчилсон. Асуултууд нь Gardner нарын SRBAI-ийн дөрвөн асуултын монгол орчуулга бөгөөд хариулт бүрийг асуултын хувилбарын дугаартай хадгалдаг. Ингэснээр өмнөх хувилбарын асуултаар авсан хариултыг шинэ хариулттай хольж шинжлэхээс сэргийлнэ.

\begin{lstlisting}[language=JavaScript, caption={SRBAI-ийн оноо тооцоолох дүрэм}]
static scoreSrbai(input: SrbaiScoreInput): SrbaiScoreResult {
  const rawAverage =
    (input.item1 + input.item2 + input.item3 + input.item4) / 4;

  const normalizedScore100 =
    Math.round(((rawAverage - 1) / 6) * 10000) / 100;

  return { rawAverage, normalizedScore100 };
}
\end{lstlisting}

\subsubsection*{Нөхцөл байдлын тогтвортой байдал}

Гүйцэтгэлийг тухайн өдөр нь бүртгэх үед \texttt{ContextSnapshotRules} нь Улаанбаатарын цагаар гүйцэтгэсэн цагийг, мөн хэрэглэгчийн сүүлийн 30 минутын байршил дадлын хадгалсан газраас 100 метрийн дотор байсан бол тэр газрын нэрийг хадгална. Өмнөх өдрийг нөхөж бүртгэхэд аль алийг нь хадгалахгүй. Тогтвортой байдлыг сүүлийн гүйцэтгэлүүдээс тооцно: цагийн хувьд хамгийн олон гүйцэтгэлийг агуулах гурван цагийн хүрээний ($\pm 1$ цаг) эзлэх хувь, газрын хувьд хамгийн түгээмэл газарт хийсэн хувь (хадгалсан газарт хийсэн гүйцэтгэл байгаа үед л). Цаг нь мэдэгдэх гүйцэтгэл 5-аас цөөн бол утгыг тооцохгүй (\texttt{null}).

\begin{lstlisting}[language=JavaScript, caption={Нөхцөл байдлын тогтвортой байдлын тооцоолол (товчилсон)}]
static computeContextStability(snapshots: Array<{
  completionHour: number | null;
  coarseLocation: string | null;
}>): number | null {
  const observed = snapshots.filter(s => s.completionHour !== null);
  if (observed.length < MIN_CONTEXT_SNAPSHOTS) return null;   // 5
  const n = observed.length;

  // Time: best 3-hour band (centre hour +-1, wrapping at midnight)
  let bestHourCount = 0;
  for (let centre = 0; centre < 24; centre += 1) {
    const count = observed.filter(
      s => hourDistance(s.completionHour!, centre) <= 1).length;
    bestHourCount = Math.max(bestHourCount, count);
  }
  const rates = [bestHourCount / n];

  // Place: only when a completion was observed at a saved place
  const places = observed.map(s => s.coarseLocation);
  if (places.some(p => p !== null)) {
    rates.push(modalCount(places) / n);
  }
  const avg = rates.reduce((a, b) => a + b, 0) / rates.length;
  return Math.round(avg * 100 * 100) / 100;
}
\end{lstlisting}

\subsubsection*{Хуваарийн биелэлт}

\texttt{computeScheduleAdherence} нь сүүлийн 28 хоногийн (дадал эхэлснээс хойш) Улаанбаатарын өдрүүдээс тухайн дадлын хуваарьт өдрүүдийг тоолж, тэдгээрийн хэдэд нь доод зорилтод хүрсэн бүртгэл байгааг тооцно. Өнөөдрийг хийсэн бол л тооцдог. Хуваарьт өдөр 7-оос цөөн бол утга \texttt{null} байна. Өмнөх хувилбарт энэ үзүүлэлтийг ``хийсэн бүртгэл / нийт бүртгэл'' гэж тооцдог байсан нь алгассан өдрийг тусгадаггүй тул зөвхөн хийсэн өдрөө бүртгэдэг хэрэглэгчид бараг 100 хувь гарч байсан.

\subsubsection*{Нийлмэл дадлын хүчний оноо}

Нийлмэл оноог 3-р бүлэгт тодорхойлсон томьёогоор тооцно. SRBAI эсвэл хуваарийн биелэлт байхгүй бол оноо тооцохгүй, ``өгөгдөл хангалтгүй'' төлөв буцаана; контекстийн тогтвортой байдал байхгүй бол үлдсэн хоёр жинг 0.85-д хуваан дахин нормчилно. Эцсийн оноог 0--39 сул, 40--69 хөгжиж буй, 70--100 хүчтэй гэж ангилна.

\begin{lstlisting}[language=JavaScript, caption={Нийлмэл дадлын хүчний онооны дүрэм (товчилсон)}]
static computeComposite(input: CompositeScoreInput): CompositeScoreResult {
  if (input.srbaiScore === null || input.consistencyScore === null) {
    return { ...base, finalScore: null, stage: 'insufficient_data' };
  }
  const parts: Array<[number, number]> = [
    [0.6, input.srbaiScore],
    [0.25, input.consistencyScore],
  ];
  if (input.contextStabilityScore !== null) {
    parts.push([0.15, input.contextStabilityScore]);
  }
  const totalWeight = parts.reduce((s, [w]) => s + w, 0);
  const weighted = parts.reduce((s, [w, v]) => s + w * v, 0);
  const finalScore = Math.round((weighted / totalWeight) * 100) / 100;

  const stage = finalScore >= 70 ? 'strong'
              : finalScore >= 40 ? 'building' : 'weak';
  return { ...base, finalScore, stage };
}
\end{lstlisting}

\subsection{Дасан зохицох зөвлөмжийн дүрэм}

\texttt{RecommendationRules} нь тухайн дадлын дохионуудаас эрэмбэлэгдсэн дүрмээр нэг үндсэн зөвлөмж сонгоно. Дүрмүүдийн эрэмбэ: зорилтыг бууруулах (\texttt{REDUCE\_TARGET}; сүүлд ``хэцүү'' гэж үнэлж, доод зорилтод хүрэх боловч үндсэн зорилтод хүрэхгүй байх), дадлыг хялбаршуулах (\texttt{SIMPLIFY\_HABIT}), сануулгаас хамаарлыг бууруулах (\texttt{REVIEW\_REMINDER\_DEPENDENCE}; гүйцэтгэлийн 70\% нь сануулгад тулгуурласан), цаг ба газрыг тогтворжуулах (\texttt{ADJUST\_CUE}; контекстийн тогтвортой байдал 40-өөс бага), дэмжлэг нэмэх (\texttt{INCREASE\_SUPPORT}), тогтвортой байдлыг бий болгох (\texttt{BUILD\_CONSISTENCY}), амжилтыг тэмдэглэх (\texttt{CELEBRATE\_CONSISTENCY}; 7, 21, 66 дахь гүйцэтгэл). Мэдээлэл дутуу (\texttt{null}) үзүүлэлт аль ч дүрмийг идэвхжүүлэхгүй. Зөвлөмж бүр тайлбар болон холбогдох суралцах нийтлэлтэй хадгалагдана. Хэрэглэгч татгалзсан зөвлөмжийг 7 хоног дахин санал болгохгүй, дараагийн тохирох дүрмийг сонгоно. Зөвлөмжийг өдөрт нэгээс илүү дахин үүсгэхгүй.

\section{Сервер талын хэсгүүдийн хэрэгжүүлэлт}

\subsection{Бүртгэл ба хандалтын модуль}

Хэрэглэгчийн бүртгэл, нэвтрэлтийг JWT-д суурилсан байдлаар хэрэгжүүлсэн. Нууц үгийг \texttt{bcrypt} ашиглан хэш хэлбэрээр хадгалдаг. Нэвтэрсний дараа хэрэглэгч токен авч, хамгаалагдсан үйлчилгээний хаягууд руу хандах боломжтой болно. Мөн хэрэглэгч зөвхөн өөрийн \texttt{userId}-тай холбоотой өгөгдөлд хандах хязгаарлалтыг сервер талд шалгадаг.

\subsection{Дадлын удирдлагын модуль}

Энэ модуль нь дадал үүсгэх, засах, архивлах, жагсаалт авах, өнөөдрийн хуваарьт дадлуудыг шүүх зэрэг үндсэн боломжуудыг агуулна. Дадлын хэмжилтийн тохиргоо, хуваарь, өдөөгч нөхцөл, хувийн шалтгаан зэрэг мэдээллийг тусдаа хүснэгтүүдэд хадгалдаг ч хэрэглэгчийн хувьд нэг логик бүтэн урсгал байдлаар ажиллана.

\texttt{GET /users/:userId/habits/today} үйлчилгээний хаяг нь тухайн өдрийн идэвхтэй хуваарьт дадлуудыг буцааж, интерфэйсийн үндсэн дэлгэцэд өнөөдрийн хийх ёстой дадлуудыг харуулахад ашиглагдана.

\subsection{Ахицын модуль}

Ахицын модуль нь гүйцэтгэл бүртгэх, бодит утгыг доод зорилт болон үндсэн зорилттой харьцуулан үнэлэх, ахицын тойм гаргах үүрэгтэй. Гүйцэтгэлийн төлөвийг сервер тооцдог: бодит утга доод зорилтод хүрвэл \texttt{DONE}, эс бөгөөс \texttt{NOT\_DONE}. Үндсэн зорилтод хүрсэн эсэхийг хадгалахгүй, интерфэйс бодит утгаас тооцож харуулна. Нэг дадалд өдөрт нэг бүртгэл байх тул тухайн өдөр бүртгэл аль хэдийн байвал шинэ бүртгэл үүсгэхгүй, хоёр утгын ихийг нь үлдээнэ. Ингэснээр давтан илгээсэн хүсэлт эсвэл хоёр төхөөрөмж бүртгэлийг давхардуулах, утгыг багасгах боломжгүй. XP болон амжилтын тэмдэг олгох алхам бүтэлгүйтсэн ч хадгалагдсан гүйцэтгэлийг алдаа гэж буцаахгүй.

Мөн ахицын тоймд дараах мэдээллийг нэгтгэн гаргадаг.

\begin{itemize}
    \item гүйцэтгэлийн хувь;
    \item өөрийн санаачилгатай гүйцэтгэлийн хувь;
    \item сануулгаас хамааралтай гүйцэтгэлийн хувь;
    \item ахицын хандлага;
    \item сүүлийн бүртгэлийн тойм.
\end{itemize}

\subsection{Сануулгын хэсэг}

Сануулгын хэсэг нь системийн зан үйлд суурилсан логикийн чухал бүрэлдэхүүн бөгөөд дараах гурван түвшинд хэрэгжсэн.

\begin{enumerate}
    \item \textbf{Шийдвэрийн түвшин} --- \texttt{ReminderDecisionRules} ашиглан сануулах эсэхийг тодорхойлох;
    \item \textbf{Гүйцэтгэлийн түвшин} --- \texttt{ReminderExecutionService} ашиглан сануулгыг бүртгэх, давхардлаас хамгаалах, хэрэглэгч рүү хүргэх;
    \item \textbf{Бодлогын түвшин} --- \texttt{ReminderPolicy} ашиглан дадлын хүч нэмэгдэхийн хэрээр сануулгын хүлээлгийн хугацааг уртасгаж, өдрийн дээд тоог багасгах (Хүснэгт~\ref{tab:tapering}).
\end{enumerate}

Сануулгад хэрэглэгч \texttt{DONE} буюу ``хийсэн'', эсвэл \texttt{SNOOZE} буюу ``хойшлуулах'' үйлдэл өгнө. Хийсэн тохиолдолд эхлээд тухайн өдрийн гүйцэтгэлийг хадгална: өдөрт бүртгэл байхгүй бол сануулгад тулгуурласан шинэ бүртгэл үүсгэж, доод зорилтод хүрээгүй бүртгэл байвал ``хийсэн'' болгоно. Үүний дараа сануулгыг гүйцэтгэгдсэн гэж тэмдэглэх тул дахин оролдоход бүртгэл давхардахгүй. Өмнөх өдрийн сануулгад ``хийсэн'' дарахыг хүлээн авахгүй. Хойшлуулсан тохиолдолд дахин сануулах хугацааг бүртгэнэ. Төхөөрөмжийн мэдэгдлийг Web Push болон VAPID түлхүүрт суурилан илгээж, хэрэглэгчийн төхөөрөмжийн бүртгэлийг сервер талд хадгалсан. Мөн нийт хэрэглэгчдэд мэдэгдэл хүргэхэд зориулж \texttt{ADMIN\_SECRET}-ээр хамгаалагдсан, хүсэлтийн тоо хязгаарлагдсан нийтэд илгээх үйлчилгээний хаягийг нэмсэн. Мэдэгдлийн бүртгэлд зөвхөн хөтчийн мэдэгдлийн үйлчилгээний HTTPS хаягийг хүлээн авдаг тул сервер дурын хаяг руу хүсэлт илгээхгүй. Хэрэглэгч системээс гарахад тухайн төхөөрөмжийн мэдэгдлийн бүртгэлийг цуцална.

\subsection{Оролцоо ба урамшууллын хэсэг}

Хэрэглэгчийн идэвхийг нэмэгдүүлэх зорилгоор XP, амжилтын тэмдэг, амжилтын мэдээллийг нэгтгэн буцаах \texttt{Engagement} хэсгийг хэрэгжүүлсэн. Тухайн хэрэглэгчийн нийт XP, нээсэн амжилтын тэмдэг, идэвхтэй төхөөрөмжийн мэдэгдлийн бүртгэлийн тоо зэрэг мэдээллийг \texttt{GET /users/:userId/engagement/summary} үйлчилгээний хаягаар хэрэглэгчийн талд өгдөг. Амжилтын үндсэн төрлүүдэд анхны гүйцэтгэл, 7 болон 21 өдрийн дараалал, нийт 30 удаагийн гүйцэтгэл зэрэг үе шатыг оруулсан.

Мөн хэрэглэгч профайл хэсгээс өөрийн нээсэн амжилтуудыг харах, амжилтын зураг болон текстийг бусад платформ руу хуваалцах боломжтой болсон. Энэ нь хэрэглэгчид ``хийсэн зүйлээ харах'' болон цааш үргэлжлүүлэх урам авах мэдрэмжийг өгөх зорилготой урамшууллын давхарга юм.

\section{Хэрэглэгчийн талын хэрэгжүүлэлт}

\subsection{Дадал үүсгэх дэлгэц}

Дадал үүсгэх интерфэйсийг ``Юу хийх вэ --- Хэзээ, ямар нөхцөлд хийх вэ --- Яагаад хийх вэ'' гэсэн гурван үндсэн ойлголтод тулгуурлан зохион байгуулсан. Ийм зохиомж нь олон салангид техникийн талбар бөглүүлэхээс илүү хэрэглэгчид ойлгомжтой урсгал бий болгох зорилготой.

Хэрэглэгч мэдээллээ оруулах үед тухайн дадлын тодорхойлолт өгүүлбэр хэлбэрээр шууд бүрэлдэн харагдана. Өмнөх үйлдлийн өдөөгч нөхцөлд ``дараа'', ``өмнө'', ``үедээ'' гэсэн цагийн байрлалыг сонгох боломжтой. Сонгосон утга нь \texttt{precedingRoutine} талбарт хадгалагдаж, дадлын дэлгэрэнгүй болон мэдэгдлийн мессежид зөв үгээрээ гарна. Мөн хэрэглэгч дадлын төрөл, олон алхам, цагийн хүрээ, байршил, хуваарь, дүрс, өнгө, шалтгаан зэрэг мэдээллийг нэг урсгалаар тохируулна.

\subsection{Профайл, санал хүсэлт ба судалгааны хэсэг}

Профайл дэлгэц нь хэрэглэгчийн ерөнхий төлөв болон системийн нэмэлт тохиргоог нэг дор төвлөрүүлсэн. Энэ хэсэгт идэвхтэй дадлын тоо, нээсэн амжилт, нийт XP, төхөөрөмжийн мэдэгдлийн зөвшөөрөл, архивласан дадлууд, өнгөний горим, санал хүсэлт, нууц үг солих, заавар дахин харах зэрэг боломжуудыг оруулсан.

Системийг 20 хэрэглэгчээр туршуулах үед чанарын болон тоон үнэлгээ авах шаардлагатай болсон. Иймээс профайл хэсэгт Google Forms судалгааны холбоосыг тусдаа ``Судалгаа'' карт хэлбэрээр байршуулсан. Ингэснээр хэрэглэгч апп дотроос шууд судалгаа бөглөж, ашиглахад хялбар байдал, сануулгын үр нөлөө, ахицын мэдээллийн хэрэгцээ, сайжруулах саналаа илгээх боломжтой болсон.

\section{Бүлгийн дүгнэлт}

Энэ бүлэгт зан үйлд суурилсан дадал хэвшүүлэх системийн хэрэгжүүлэлтийг тайлбарлав. Үүнд технологийн багц, кодын сангийн бүтэц, өгөгдлийн сан, сануулгын шийдвэр ба бодлогын дүрэм, гүйцэтгэлийн эх үүсвэрийн ангилал, дадлын хүчний тооцоолол, дасан зохицох зөвлөмж, төхөөрөмжийн мэдэгдэл, урамшууллын хэсэг, сервер болон хэрэглэгчийн талын үндсэн дэлгэцүүд, API-ийн зохион байгуулалт зэргийг авч үзлээ.

Хэрэгжүүлэлтийн үр дүнд бүртгэл, дадал үүсгэх/засах, цагийн хүрээ болон байршлын өдөөгч нөхцөл тохируулах, гүйцэтгэл бүртгэх, сануулга илгээх ба аажмаар бууруулах, SRBAI үнэлгээ авах, дадлын хүч тооцоолох, ахицын мэдээлэл боловсруулах, зөвлөмж гаргах, XP болон амжилтын тэмдэг олгох, санал хүсэлт авах зэрэг боломжууд ажиллах түвшинд хүрсэн. Мөн \texttt{ReminderDecisionRules}, \texttt{CueWindowRules}, \texttt{TriggerSourceRules}, \texttt{HabitStrengthRules}, \texttt{RecommendationRules} зэрэг зан үйлийн дэмжлэгийн дүрмүүдийг нэгжийн тесттэйгээр бодит кодын түвшинд хэрэгжүүлснээр өмнөх бүлгүүдэд боловсруулсан онолын загварыг турших боломжтой програм хангамжийн шийдэл болгон буулгасан.
